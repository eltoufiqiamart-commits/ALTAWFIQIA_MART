# دليل النشر — EL TAWFIKIA MART

النشر المجاني على **Supabase (Free)** + **Vercel (Hobby)**. اتبع الخطوات بالترتيب.

## 1) إنشاء مشروع Supabase

1. أنشئ مشروعًا جديدًا على [supabase.com](https://supabase.com) واختر أقرب منطقة (أوروبا الوسطى مثالًا لخدمة مصر بزمن معقول).
2. سجّل:
   - Project URL مثل `https://xxxxxxxx.supabase.co`
   - **anon public key**
   - **service_role key** (سري، خادم فقط — لا يصل للمتصفح أبدًا)


> ملاحظات على الترحيلات الجديدة:
> - `0016` يفرض مسار الإيصال `receipts/<auth.uid()>/<uuid>.(jpg|png|webp|pdf)` داخل قاعدة البيانات نفسها.
> - `0018` يلغي صلاحيات تنفيذ الدوال الداخلية ويجعل دوال ما بعد النشر تبدأ **بدون صلاحية عامة**؛ أي دالة RPC جديدة للعملاء تحتاج `grant execute ... to anon, authenticated` صريح (كما يفعل `0019`).
> - `0019` يضيف `preview_coupon(text, bigint)` لمعاينة الكوبون دون فتح جدول `coupons` للعملاء.
> - `0020` **سلامة البيانات التاريخية**: يضيف لقطة ثابتة لكل سطر طلب
>   (`cost_amount_at_order` + بيانات المورّد وقت الطلب) فتظل أرباح الطلبات
>   القديمة صحيحة حتى لو تغيّرت تكلفة المنتج أو مورّده لاحقًا؛ ويمنع تسليم طلب
>   مدفوع مسبقًا قبل تأكيد دفعه، ويمنع إلغاء طلب مدفوع دون مسار استرداد، ويوسّع
>   الإلغاء التلقائي ليشمل حالة `awaiting_verification`.
>   الأعمدة الجديدة **للإدارة فقط** ويجب ألا تظهر في أي استعلام للعملاء.
> - `0021` **تحصين حدّ المعدل**: كان `check_rate_limit` قابلًا للتنفيذ من أي
>   زائر مع تمرير الحد والنافذة بنفسه (أي تعطيل الحماية كليًّا) وكتابة صف لكل
>   طلب. صار الحد والنافذة داخل جدول `rate_limit_buckets` على الخادم، والدالة
>   العامة الوحيدة `consume_rate_limit(bucket, discriminator)` لا تقبل حدودًا
>   من المتصل، وتستخدم عدّادات نوافذ ثابتة بدل صف لكل طلب.
> - `0022` **معاملات ذرّية + خصوصية الإعدادات**: استبدال توافق المركبات صار
>   داخل معاملة واحدة (كان DELETE ثم INSERT بلا تراجع)، وجدول
>   `business_settings` لم يعد مقروءًا بالكامل للجميع: فقط الصفوف المعلّمة
>   `is_public` (مفتاح `pricing` صار خاصًّا).
> - `0023` **دورة حياة التخزين**: سجل `storage_objects_pending` يرصد أي ملف
>   مرفوع لم يُربط بسجل حقيقي (إيصال لطلب لم يكتمل مثلًا)، ووظيفة الصيانة تحذف
>   فقط ما تجاوز مهلة 48 ساعة **ولا يزال غير مرتبط** بأي صف.
> - `0024` **سياسة هامش الربح**: قيد `costs_sane` كان يقارن التكلفة بسعر
>   القائمة فقط، فكان بيع منتج بخصم 90% تحت التكلفة ممكنًا دون أي تنبيه. صار
>   هناك مفتاح `margin_policy` (خاص) بثلاثة أوضاع: `warn` (الافتراضي — يسمح
>   بالبيع ويسجّل التنبيه في `margin_alerts`)، و`block` (يرفض الحفظ)، و`off`.
>   الوضع الافتراضي **لا يغيّر أي سلوك حالي**، بل يضيف رؤية فقط. جدول
>   `margin_alerts` **للإدارة فقط**.
> - `0025` **تصحيح مطابقة المسارات**: مُطالِبة صور المنتجات كانت تستخدم
>   `like '%' || path` و`_` داخل المسار يعمل كمحرف بدل؛ صارت مطابقة حرفية
>   بـ `right()`. (دلو الإيصالات اسمه `private` وليس `receipts`.)
> - `0026` **سحب صلاحية زائدة**: كان `claim_pending_object` ممنوحًا لكل مستخدم
>   مسجَّل وبلا أي فحص ملكية، فكان بإمكان أي عميل تعليم أي ملف بأنه "مرتبط"
>   فيَسلم من التنظيف نهائيًّا (استنزاف تخزين). سُحبت الصلاحية — ولا يستدعيها
>   كود التطبيق أصلًا لأن المطالبة تتم عبر المشغّلات تلقائيًّا.
> - `0027` **الوضع الافتراضي لسياسة الهامش صار `block`**: منع حفظ أي سعر نهائي
>   تحت التكلفة بدل الاكتفاء بالتسجيل. المنتجات الموجودة تحت التكلفة **تبقى
>   معروضة وقابلة للبيع**؛ المنع يسري فقط على تعديل السعر/الخصم/التكلفة.
>   الترحيل يطبع عدد المنتجات المتأثرة قبل التبديل. لتخفيض ترويجي متعمَّد:
>   `update business_settings set value = jsonb_set(value,'{mode}','"warn"') where key='margin_policy';`
>   ثم أعِده إلى `block`. و`minMarginBps` يفرض هامشًا أدنى موجبًا (500 = 5%).
> - `0028` **سباق مفتاح عدم التكرار**: `place_order` كان يفحص ثم يُدرج، فطلبان
>   متزامنان بنفس المفتاح يمرّان معًا. قيد التفرّد يمنع الطلب الثاني فعلًا (سلامة
>   البيانات محفوظة) لكن الخطأ كان يظهر للعميل كـ"خطأ غير متوقع" رغم **نجاح**
>   طلبه — فيعيد المحاولة بمفتاح جديد ويُنشئ تكرارًا حقيقيًّا. صارت الدالة
>   غلافًا يلتقط `unique_violation` ويعيد نفس استجابة الإعادة. التنفيذ الفعلي
>   انتقل إلى `_place_order_impl` (داخلي، غير قابل للاستدعاء من العملاء).

## 3) إعدادات Auth

في **Authentication → URL Configuration**:

- Site URL: رابط موقعك على Vercel مثل `https://tawfiqia-mart.vercel.app`
- Redirect URLs (تطابق مسارات التطبيق):
  - `https://<your-domain>/auth/confirm`
  - `http://localhost:3000/auth/confirm` (للتطوير المحلي)

في **Authentication → Providers**: فعّل البريد/كلمة المرور (الباقي يُضاف لاحقًا بسهولة).
ننصح بإيقاف التأكيد عبر البريد أو ربط SMTP حقيقي مجاني (Resend/ Brevo) بحسب سياسة المتجر.

## 4) Storage

الترحيل `0006_storage.sql` ينشئ Bucketين:

- `products` — عام للقراءة (صور المنتجات والبانرات). الرفع خادم فقط عبر Route Handlers بفحص نوع الملف بالـ magic bytes وإعادة ضغط WebP.
- `private` — خاص تمامًا (إيصالات التحويل والملفات الحساسة)، لا قراءة مباشرة للمستخدمين؛ تُصدر روابط موقّعة قصيرة العمر للإدارة بعد التحقق من الصلاحية.

لا تُضف سياسات رفع مباشرة للعملاء.

## 5) متغيرات البيئة على Vercel

Project → Settings → Environment Variables، ثم أضف محتويات `.env.example`:

| المتغير | عام؟ | القيمة |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | نعم | رابط المشروع |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | نعم | مفتاح anon |
| `SUPABASE_SERVICE_ROLE_KEY` | **لا** | مفتاح service_role |
| `SUPER_ADMIN_EMAILS` | لا | بريدك (أو عدة بريدات مفصولة بفواصل) |
| `NEXT_PUBLIC_SITE_URL` | نعم | رابط النشر النهائي |
| `SITE_URL` | لا | نفس الرابط للاستخدام الخادمي |
| `CRON_SECRET` | لا | سر عشوائي طويل لوظيفة الصيانة المجدولة (`openssl rand -hex 32`) |

تنبيهات أمان:

- أي متغير يبدأ بـ `NEXT_PUBLIC_` يُحزَّم للمتصفح؛ لذلك لا يوضع فيه أي سر.
- مفتاح service_role يتجاوز RLS؛ وجوده محصور في Server Actions وRoute Handlers بعد فحص الصلاحيات.

## 6) النشر على Vercel

1. ارفع المستودع إلى GitHub واستورد المشروع على Vercel.
2. إطار العمل يُكتشف تلقائيًا (Next.js 15). **إصدار Node المطلوب 22.x**
   (Project → Settings → General → Node.js = 22.x؛ مُثبَّت أيضًا في `engines` بـ package.json).
3. البناء: `npm run build` (فحص الأنواع وESLint يُنفَّذان عبر `npm run typecheck` و`npm run lint` انظر قسم الفحوصات أدناه).
4. عند التشغيل الذاتي لبصمة `output: standalone`، أي ملف `.env` داخل مجلد البناء يُنسَخ حرفيًا إلى الناتج — لا تضع أسرارًا في ملفات تُنسب للمستودع؛ على Vercel تُحقن المتغيرات من لوحة المشروع فقط.
5. بعد أول نشر، سجّل الدخول بالبريد المدرج في `SUPER_ADMIN_EMAILS`، ثم افتح `/admin` (لا يوجد أي رابط إدارة في الواجهة العامة).

> على بيئات البناء الصغيرة (~2GB RAM) قُسّم فحص الأنواع إلى ثلاث مشاريع:
> `npm run typecheck` يشغّلها كلها. هذا سبب ضبط `typescript.ignoreBuildErrors`
> و`eslint.ignoreDuringBuilds` في `next.config.mjs`؛ الفحص الحقيقي يتم في سكريبتات الـ CI الصريحة.

## 7) إعداد مجاني موصى به بعد النشر

### الصيانة المجدولة (Vercel Cron)

ملف `vercel.json` يُعرّف وظيفة يومية الساعة 01:00 توقيت UTC تستدعي
`GET /api/cron/maintenance` وتقوم بـ:

1. إلغاء الطلبات المدفوعة مسبقًا (محافظ/تحويل) التي ظلت `pending` بحالة
   دفع `unpaid` أكثر من 24 ساعة، مع إفراج حجز المخزون ذرّيًا، وإعادة استخدام
   الكوبون، وتعليم الدفعة `failed`، وإشعار العميل. طلبات الدفع عند الاستلام
   والطلبات التي أُرسل عنها إيصال (`awaiting_verification`) لا تُلغى تلقائيًا.
2. حذف صفوف `rate_limit_events` الأقدم من 7 أيام.

الحماية: Vercel يرسل تلقائيًا الترويسة `Authorization: Bearer $CRON_SECRET`
عند ضبط المتغير، والدالتان في قاعدة البيانات ترفضان أي دور غير `service_role`.

- بعد ضبط `CRON_SECRET` في Vercel → Settings → Environment Variables وأول نشر،
  اختبر التشغيل اليدوي (ينفّذ نفس مسار اليومية):
  `curl -H "Authorization: Bearer $CRON_SECRET" https://YOUR_DOMAIN/api/cron/maintenance`
- بدون ضبط المتغير يعيد المسار 503 (لا يعمل أحد غير المصرح له).
- الدفعات اليومية مجانية ضمن باقة Vercel Hobby (مهمة يومية واحدة).

### ملاحظات أخرى

- جدول `rate_limit_events` ينظّف نفسه ذاتيًا أثناء التشغيل (تحذف الدالة الأحداث
  الأقدم من نافذة كل bucket)، والوظيفة اليومية تحذف المتبقي الأقدم من 7 أيام.
- في Supabase اضبط الـ Database webhooks / بريد التأكيد حسب الحاجة.
- اربط نطاقك الخاص ثم حدّث Site URL وRedirect URLs.
- راقب Storage: خطة Supabase المجانية 1GB؛ صور المنتجات تُضغط WebP تلقائيًا (حد 5MB للملف الأصلي).

## 8) اختبارات الأمان العدائية

بعد تطبيق كل الترحيلات، نفّذ `docs/SECURITY-TESTS.sql` في SQL Editor بعد استبدال
معرفي عميلين تجريبيين، وتأكد أن كل النتائج تُظهر PASS (عزل الطلبات، الأعمدة
الخاصة، نطاق مسار الإيصالات، الدوال الداخلية غير قابلة للتنفيذ، عدم الكتابة
المباشرة للجداول المحمية).

لتجهيز الملف دون تعديل يدوي (يتحقق من صحة المعرّفين ومن اختلافهما):

```bash
# احصل على المعرّفين: select id, email from auth.users order by created_at;
node scripts/prepare-security-tests.mjs <CUSTOMER_A_UUID> <CUSTOMER_B_UUID>
# ينتج docs/SECURITY-TESTS.ready.sql — الصقه في SQL Editor ونفّذه بالكامل
```

كل جزء في المجموعة ملفوف بمعاملة تُلغى (rollback) فلا تتغير أي بيانات. احذف
`docs/SECURITY-TESTS.ready.sql` بعد الانتهاء لأنه يحتوي معرّفات مستخدمين حقيقية
(وهو مستثنى من git أصلًا). أعد تشغيل المجموعة بعد أي تعديل على RLS أو دوال RPC.

## 9) التحقق النهائي

- [ ] لا يوجد أي سعر أو تكلفة أو مخزون محجوز يصل للعميل (راجعت الشبكة في تبويب المتصفح).
